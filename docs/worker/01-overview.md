# Worker Service - الفكرة العامة

## ايه هو الـ Worker؟

الـ Worker هو **سيرفر مستقل** مسؤول عن **استضافة وتشغيل ملفات PHP** اللي بيرسلها المستخدمين عن طريق البوت الأساسي على تيليجرام.

ببساطة: البوت الأساسي بيعمل "نقل" — بيبعت الملف للـ Worker، والـ Worker بيشغله وبيرد على تيليجرام.

---

## ليه Worker منفصل؟

```
❌ من غير Worker:
    البوت الأساسي بيشيل كل حاجة → لو حصل حاجة للبوت، كل حاجة بتقف

✅ مع Worker:
    البوت الأساسي = إدارة المستخدمين والملفات
    Worker = تشغيل PHP بس
    لو Worker وقف → البوت الأساسي يكمل شغال
    لو Worker اتقفل → يتعمل واحد تاني بسرعة
```

## كل Endpoint بيعمل ايه؟

### 1. `POST /deploy` — تشغيل بوت جديد

```
البوت الأساسي بيبعت:
  • user_id      → رقم المستخدم
  • bot_token    → توكن البوت من تيليجرام
  • file         → ملف الـ PHP

الـ Worker بيعمل:
  1. يحفظ الملف في /app/user_bots/{user_id}/bot.php
  2. يولّد webhook_secret (سر خاص بالـ webhook)
  3. يسجل الـ webhook على تيليجرام
  4. يحفظ بيانات البوت في bots.json
  5. يرجع {"status": "ok"}
```

### 2. `POST /stop` — إيقاف بوت

```
البوت الأساسي بيبعت:
  • user_id → رقم المستخدم

الـ Worker بيعمل:
  1. يحذف الـ webhook من تيليجرام
  2. يغيّر حالة البوت لـ "stopped"
  3. يرجع {"status": "ok"}
```

### 2.5. `POST /delete` — حذف البوت بالكامل

```
البوت الأساسي بيبعت:
  • user_id → رقم المستخدم

الـ Worker بيعمل:
  1. يتحقق من السر (X-Internal-Secret)
  2. يبحث عن البوت في bots.json
   3. يحذف الـ webhook من تيليجرام
   4. يمسح فولدر المستخدم بالكامل (user_bots/{user_id}/)
   5. يزيل البوت من bots.json
   6. يرجع {"status": "ok"}

   > **ملاحظة على الترتيب:** يُمسح الفولدر قبل حذفه من `bots.json`. إذا فشل
   > حذف الفولدر (أذونات، ملفات مشغولة) يبقى البوت مسجل ويمكن إعادة المحاولة.
```

### 2.6. `POST /files/delete` — حذف ملف معيّن

```
البوت الأساسي بيبعت:
  • user_id   → رقم المستخدم
  • filename  → اسم الملف اللى عايز تمسحه (مثلاً: bot.php)

الـ Worker بيعمل:
  1. يتحقق من السر (X-Internal-Secret)
  2. يتأكد إن الـ filename ما فيه غير اسم الملف (بدون مسارات)
  3. يتأكد إن الـ filename .php بس
  4. يمسح الملف من فولدر المستخدم
  5. يرجع {"status": "ok"}
```

### 3. `GET /status/{user_id}` — معرفة حالة البوت

```
البوت الأساسي بيبعت:
  • user_id في الـ URL

الـ Worker بيرجع:
  • "running"  → البوت شغال
  • "stopped"  → البوت موقف
  • "not_found" → مفيش بوت بالرقم ده
```

### 4. `POST /webhook/{user_id}` — استقبال Updates من تيليجرام

```
تيليجرام بيبعت:
  • Update JSON في الـ body
  • X-Telegram-Bot-Api-Secret-Token في الـ header

الـ Worker بيعمل:
  1. يتأكد إن البوت موجود وشغال
  2. يتحقق من الـ secret_token
  3. يتأكد إن الـ JSON صحيح
  4. يبعت الـ update لـ Caddy → PHP-FPM
  5. PHP بتشتغل في فولدر المستخدم
  6. يرجع الرد لتيليجرام
```

## الاتصال بين القطع

```
البوت الأساسي ←→ Worker:
  • كل الـ API endpoints محمية بـ X-Internal-Secret
  • البوت الأساسي لازم يبعت السر ده في كل request

Worker ←→ تيليجرام:
  • لما Worker يستقبل /deploy، بيسجل webhook على تيليجرام
  • تيليجرام بيبعت updates لـ /webhook/{user_id}
  • كل بوت ليه سر خاص (webhook_secret) بيتحقق منه Worker

Worker ←→ PHP-FPM:
  • Worker بيتصل بـ Caddy على البورت الداخلي 9000
  • Caddy بيتصل بـ PHP-FPM عن طريق Unix socket
  • PHP بتشتغل بـ open_basedir محدود لفولدر المستخدم
```

## الفولدرات والملفات المهمة

```
/app/
├── main.py              # الكود الرئيسي (FastAPI)
├── data/
│   └── bots.json        # بيانات البوتات (user_id, token, status)
├── user_bots/
│   ├── 12345/
│   │   ├── bot.php      # ملف بوت المستخدم 12345
│   │   ├── config.json  # {"bot_token": "...", "compat": true}
│   │   └── error.log    # لوجات البوت (يُكتب عليها مرة لما يحصل خطأ)
│   ├── 67890/
│   │   └── bot.php      # ملف بوت المستخدم 67890
│   └── ...
└── logs/
    └── supervisord.log  # لوجات التشغيل
```

> الفولدر `user_bots/{user_id}/` كامل بيُمسح بالكامل عبر `POST /delete`.
> أما الملف داخله (مثل `bot.php`) فيُمسح فردياً عبر `POST /files/delete`.

## الـ Environment Variables

| المتغير | الشرح | مثال | من فين؟ |
|---------|-------|------|---------|
| `INTERNAL_SECRET` | السر المشترك بين البوت الأساسي والـ Worker | `my_secret_key_123` | **تنشئه أنت** في Railway Variables |
| `RAILWAY_PUBLIC_DOMAIN` | الدومين اللي Railway بيديه للـ Worker | `worker-production-abc.up.railway.app` | Railway بيحدده تلقائياً |
| `MAIN_BOT_URL` | عنوان البوت الأساسي | `https://main-bot.up.railway.app` | **تنشئه أنت** في Railway Variables |
| `PORT` | البورت العام (بيتحدد تلقائياً من Railway) | `8000` | Railway بيحدده تلقائياً |

**ملاحظة مهمة:** `INTERNAL_SECRET` و `MAIN_BOT_URL` مش متغيرات Railway جاهزة — لازم تنشئهم يدوياً من Railway dashboard → service → Variables → New Variable.

## ازاي بيشتغل على Railway؟

```
1. Railway بيعمل build للـ Dockerfile
2. Docker بيثبت: Python + PHP-FPM + Caddy
3. supervisord بيشغل 3 processes:
   • PHP-FPM (بيستقبل طلبات PHP)
   • Caddy (بيعمل reverse proxy)
   • FastAPI (بيستقبل API requests)
4. Railway بيدي الـ Worker URL عام
5. لما Worker يبدأ، بيبعت لـ البوت الأساسي:
   POST {MAIN_BOT_URL}/worker/register
   { "worker_url": "https://...", "secret": "..." }
6. البوت الأساسي بيعرف إن Worker جديد جاهز
7. لما مستخدم يطلب تشغيل بوت، البوت الأساسي بيبعت /deploy
```

## ملخص

| المكون | الوظيفة |
|--------|---------|
| **FastAPI** | بيستقبل API requests من البوت الأساسي + webhooks من تيليجرام |
| **Caddy** | بيعمل routing + بيتكلم مع PHP-FPM |
| **PHP-FPM** | بيشغل ملفات PHP بمعزل كامل |
| **supervisord** | بيدير كل العمليات ويعيد تشغيلها لو حصل مشكلة |
| **Docker** | بيجمع كل حاجة في container واحد |
| **Railway** | بيستضيف الـ container ويديه URL عام |
